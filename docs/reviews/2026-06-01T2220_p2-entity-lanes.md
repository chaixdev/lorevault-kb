## Section 1 — Summary

The Entity Lanes exhibit a disciplined copy-paste architecture — 6 lanes with structurally identical persistence and consolidation patterns. The review uncovered **1 CRITICAL** normalization divergence that silently breaks connected-components clustering, plus **7 HIGH** and **16 MEDIUM** findings spanning correctness, observability, structural drift, and copy-paste inconsistencies.

**Resolution:** All findings addressed. 5 CRITICAL/HIGH fixes applied in `00293a7` (normalization, retry, provenance, null guards, package move). HIGH-1 deferred for domain decision then resolved in `53bd788` (standardized all lanes to DELETE on zero mentions). 16 MED/LOW fixes in `f0e4730` (logging, dead code, Lombok, sanitization, naming). MED-14 (11 interface removal) in `b67c70b`. P1 Step→Stage refactor in `3ded5fdf`. Guidance gaps codified in `c665354` across 5 docs. 2 findings rejected (HIGH-5 Event drift, HIGH-7 LLM name in log) — by design. 3 deferred (MED-10, LOW-1/2 — dedicated logging pass, book-scope planning).

**Retrospective:** 8 of 17 findings were violations of existing guidance (the rules were correct; the review caught drift). 8 were genuine guidance gaps (no rule existed); those have been codified. 1 was copy-paste naming drift. This is a healthy split — about half the review's value was enforcement of known standards, half was discovering what standards were missing.

## Section 2 — Findings

### CRITICAL

#### CRIT-1 — Normalization divergence silently breaks connected-components clustering
**Severity:** 🔴 CRITICAL
**Files:** `orchestration/consolidation/NameKeys.java:62`, `common/NameNormalizer.java:20`
**Cross-track:** Track A (LOGIC-1) + Track B (DATA-1)
**Problem:** `NameKeys.normalizeName()` does trim + collapse whitespace + lowercase. `NameNormalizer.normalize()` does trim + collapse whitespace + lowercase + **strip punctuation**. Persistence stores `normalizedName` via `NameNormalizer` (punctuation-stripped, e.g. `"dr smith"`). During consolidation, aliases are normalized by `NameKeys.normalizeName()` (punctuation-preserved, e.g. `"dr. smith"`). When both are combined into a single key set by `NameKeys.from()`, the different normalizations create key-space divergence that can cause entities sharing semantic names to fail transitive clustering — producing split entities where the system should produce one.

**Fix:** Having two normalizers is the real bug. Delete `NameKeys.normalizeName()` entirely and use only `NameNormalizer.normalize()` from `common`. The `from()` method in `NameKeys` should call `NameNormalizer.normalize(alias)` instead of `normalizeName(alias)`.

**New rule:** `common` is the canonical library for string validation, formatting, and normalization utilities. Any new normalization/sanitization/formatting method should go there, and all existing code should converge on `common` methods over inline or duplicated logic. `NameNormalizer.normalize()` is the first entry in this library.

### HIGH

#### HIGH-1 — Inconsistent delete-on-zero-mentions behavior across lanes
**Severity:** 🟠 HIGH
**Files:** `object/consolidation/chapter/ChapterObjectConsolidationService.java`, `collective/consolidation/chapter/ChapterCollectiveConsolidationService.java`, `concept/consolidation/chapter/ChapterConceptConsolidationService.java`, `individual/consolidation/chapter/ChapterIndividualConsolidationService.java`, `event/consolidation/chapter/ChapterEventConsolidationService.java`, `location/consolidation/chapter/ChapterLocationConsolidationService.java`
**Problem:** When `mentionCount == 0`, 3 lanes (Object, Collective, Concept) **delete** existing chapter-level consolidated entities and return `success=true`. 3 lanes (Individual, Event, Location) **skip deletion** and return `success=false`. Re-running ingestion on a chapter whose LLM extraction now returns zero mentions silently wipes data for half the entity types while preserving it for the other half, with no warning to the caller. This is a correctness inconsistency — the zero-mentions case should have the same semantic treatment across all lanes.

**Fix:** Standardize. Either: (a) all lanes delete on zero mentions (treat absence of data as ground truth), or (b) all lanes skip deletion (treat absence as possibly transient). Document the chosen semantic in the consolidation design doc. If the difference is intentional (some entity types can legitimately hit zero mid-book), add an ADR justifying the lane-specific behavior.

**Disposition:** FIXED (`53bd788`). Decision: rerun should not leave stale state. All 6 lanes now DELETE + return `success=true` on zero mentions. Note: this is an implementation decision — the incremental ingestion refactor may handle this differently. Not codified as a guidance rule (it's not portable, and the "all lanes identical" mandate is copy-paste fidelity enforcement, not a standalone rule).

#### HIGH-2 — Missing retryability classification in 4 of 6 chapter consolidation handlers
**Severity:** 🟠 HIGH
**Files:** `object/consolidation/chapter/ChapterObjectConsolidationHandler.java:69`, `location/consolidation/chapter/ChapterLocationConsolidationHandler.java:63`, `individual/consolidation/chapter/ChapterIndividualConsolidationHandler.java:64`, `collective/consolidation/chapter/ChapterCollectiveConsolidationHandler.java:69`
**Cross-track:** Track A (LOGIC-3) + Track C (ASYNC-1/2/3/4) + Track E (STRUCT-6)
**Problem:** These 4 handlers catch all exceptions and return `StepResult.failure()` (non-retryable), with no `isRetryableError()` method. The other 2 handlers (`ChapterConceptConsolidationHandler`, `ChapterEventConsolidationHandler`) and all 5 book-level handlers have `isRetryableError()` — classifying transient API failures (rate-limit, connection timeout) for retry. This means transient failures in 4 of 6 entity lanes are permanently recorded as failures, blocking pipeline progression. Additionally, `BookEventAnnCandidateException` wraps transient failures but uses a static message — the `isRetryableError()` methods only check `e.getMessage()` on the top-level exception (never unwrapping causes), so wrapped transient failures are misclassified as permanent.

**Fix:**
1. Add `isRetryableError(Exception)` to each of the 4 missing handlers, matching the pattern in `ChapterConceptConsolidationHandler`.
2. Fix `BookEventAnnCandidateException` to include the cause's message.
3. Make all `isRetryableError()` methods recursively unwrap `getCause()` when checking for transient indicators.
4. Extract `isRetryableError` into a shared utility (`ConsolidationErrorClassifier`) to eliminate 9 identical copies.

#### HIGH-3 — stageId=null violates durable provenance contract
**Severity:** 🟠 HIGH
**Files:** `individual/consolidation/chapter/ChapterIndividualConsolidationOperation.java`, event chapter consolidation equivalent
**Problem:** The default `execute(UUID chapterId, UUID jobId)` method on `ChapterIndividualConsolidationOperation` creates `StageExecutionContext` with `stageId=null`. The pipeline's documented contract requires `stageId` as the durable provenance identity tagged on every created entity node. All entities created through this convenience code path have null provenance, breaking audit trails and stage-output lookups.

**Fix:** Remove the default convenience method `execute(UUID, UUID)` from `ChapterIndividualConsolidationOperation`. Callers must use the full `execute(StageExecutionContext)` path which carries `stageId`. If the convenience method exists for test/diagnostic commands, those callers should construct `StageExecutionContext` directly with a valid `stageId`.

#### HIGH-4 — No null-guards on LLM extraction list elements across all 6 persistence services
**Severity:** 🟠 HIGH
**Files:** All 6 `*PersistenceService.java` files (Individual, Collective, Concept, Location, Object, Event)
**Problem:** All 6 persistence services iterate LLM extraction lists with `extractions.get(extractionIndex)` and immediately call `.aliases()`, `.sceneId()`, etc. on the element — with no null check on the individual element. A malformed LLM response containing null entries in the extraction list causes `NullPointerException`, crashing the handler with no recovery path. Only `LocationPersistenceService` has a guard on one field; others have none.

**Fix:** Add a `if (extracted == null) { log.warn(...); continue; }` guard immediately after `extractions.get(index)` in the extraction loop across all 6 services.

#### HIGH-5 — Event lane structural drift from peer lanes
**Severity:** 🟠 HIGH
**Files:** `event/consolidation/book/` (package), `event/persistence/BookEvent.java`
**Problem:** Two structural divergences:
1. Event is the only lane missing `BookEventConsolidationHandler` and `BookEventConsolidationOperation`. All 5 other lanes have a handler implementing a lane-specific Operation interface with claim acquisition, retryable error handling, and structured logging. Event's book-level handler (`BookEventCandidateGenerationHandler`) implements `StageOperation` directly — a different contract.
2. `BookEvent` record is missing fields present in all other `Book*` records: `aliases`, `chapterEventCount`, `representativeChapterEventId`, `firstSeenChapterId`. This structural drift lacks documented justification.

**Fix:** ~~Either add the missing handler/operation following the common pattern, or document this intentional divergence in an ADR explaining why Event's book-level consolidation follows a different architecture. Evaluate whether the missing fields should be added to `BookEvent`.~~

**Disposition:** REJECTED. Event is an exceptional entity type. It remains classified as an entity lane to make it pluggable in the same retrieval path, but its ingestion path is different by design. The structural divergence from other lanes (different book-level handler contract, different BookEvent record shape) is intentional, not drift. No change needed.

#### HIGH-6 — BookConsolidationClaim lives in wrong package
**Severity:** 🟠 HIGH
**Files:** `location/consolidation/book/BookConsolidationClaim.java` (and 3 sibling files)
**Problem:** `BookConsolidationClaim`, `BookConsolidationClaimService`, `BookConsolidationClaimRepository`, and `BookConsolidationClaimUnavailableException` are defined in `location.consolidation.book` but are consumed by ALL 6 lanes via cross-package imports. This is a package boundary violation — shared infrastructure hidden inside a lane-specific package.

Note: the planned book-scope incremental processing refactor will likely touch these files too, so this move may be temporary — but it's still worth doing now to resolve the boundary violation.

## Section 4 — Test Gaps

Tests were not read as part of this review pass. Based on production findings, the following test scenarios are likely absent and should be added:

- ⚠️ **Normalization equivalence test** — verify that `NameKeys.normalizeName("Dr. Smith")` and `NameNormalizer.normalize("Dr. Smith")` produce identical keys, or that consolidation correctly clusters entities whose keys differ only by punctuation
- ⚠️ **Zero-mentions behavior test** — verify consistent behavior across all 6 lanes when `mentionCount == 0` (either all delete or all preserve)
- **Null element in LLM extraction list** — verify every persistence service handles null entries in the extraction list without NPE
- **Malformed UUID test** — verify UUID.fromString() in persistence services handles non-UUID strings from LLM output gracefully
- **Retryable exception classification** — verify `isRetryableError()` in all 6 chapter handlers correctly identifies rate-limit, timeout, and connection-refused exceptions; verify wrapped exceptions are unwrapped
- **Claim release ordering** — verify claim is released in DB before the in-memory token is removed
- **Handler idempotency** — verify `ChapterEventEmbeddingHandler` skips reprocessing when all events are already embedded
- **Log sanitization** — verify no LLM output content appears in log statements (specifically `ConceptPersistenceService`)
- **Structural parity** — verify Event lane has equivalent consolidation handler/operation interface pattern to peer lanes

## Section 9 — Retrospective: Guidance Gaps vs Enforcement

Of 28 total findings, 11 were excluded (rejected, deferred, or investigated). Of the remaining 17 actionable findings:

| Cause | Count | Examples |
|-------|-------|----------|
| **Existing guidance violated** | 8 | HIGH-4 (null guards), MED-6 (idempotency), MED-8 (jobId), MED-12 (dead code), MED-13 (@Data on entity), MED-14 (single-impl interfaces), MED-9/LOW-7 (inconsistent sanitization) |
| **Guidance gap — no rule existed** | 8 | CRIT-1 (dual normalizers), HIGH-2 (retry classification mandate), HIGH-6 (cross-lane type placement), MED-2/LOW-4 (type-as-identity), MED-4 (unbounded Cypher), MED-5 (Neo4jClient/SDN mixing), MED-7 (service write logging), MED-16 (@Slf4j mandate) |
| **Copy-paste drift** | 1 | MED-15 (chooseDisplayName vs firstNonBlankAlias) |

**Key takeaway:** About half the review's value was catching drift from known standards; half was discovering what standards were missing. Both are healthy signals — the guidance is broadly correct, and the review process surfaces gaps faster than they accumulate. The 8 gaps have been codified into 5 docs: `coding-standards.md` (3 rules), `exception-semantics.md` (1 rule), `logging-philosophy.md` (1 rule), `lorevault-module-conventions.md` (1 rule), `code-organization-guidance.md` (2 rules).

**Not codified:** HIGH-1 (delete-on-zero-mentions) is an implementation decision, not a rule — the incremental ingestion refactor may handle it differently. It was standardized now to match the current paradigm (rerun must not leave stale state), but the "all lanes identical" mandate is copy-paste fidelity enforcement, not a standalone rule.
